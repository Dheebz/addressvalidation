# Local operations

Open the [G-NAF Control Centre](http://127.0.0.1:8081/) after the local stack is started. Its status banner shows the national release and whether address lookups are responding. The database and API panels update every ten seconds. The database panel shows which node is serving, which is ready to take over, whether the standby is caught up, and how many failover coordinators are online. "Automatic takeover ready" requires both database nodes, streaming replication, and coordinator quorum. The API panel shows whether both API servers are ready. When one is offline, the gateway sends new requests to the other.

## Access and operator history

The Compose portal is a **local development** control centre, published only on `127.0.0.1:8081`. In that mode it has no sign-in, so do not expose the port to a network. Browser forms carry antiforgery tokens; a stale page after a container restart should be refreshed before retrying an action.

Outside Development, the admin process refuses to start unless `AdminAuth:Authority` (HTTPS OIDC issuer), `AdminAuth:ClientId`, `AdminAuth:ClientSecret`, and `AdminAuth:KeysDirectory` are configured. The identity provider must issue the `Address.Admin` role in its `roles` claim. The admin web origin must use HTTPS and register `/signin-oidc` as its redirect path. Mount the key directory persistently and share it among admin replicas so cookies and form tokens survive restarts. Keep the client secret and key directory out of source control; use the eventual cloud secret and key storage when Azure is provisioned. Do not enable production mode on the public network until the identity provider, HTTPS ingress, key storage, and operator access have been tested together.

The **Recent operator actions** panel shows the latest 20 preparation requests, release switches, rollbacks, retained-release deletions, and bulk retention changes, including outcome, actor, time, and request ID. This history is stored in `platform.admin_event` and is also available to signed-in administrators at `GET /api/events`. Background preparation completion or failure is attributed to `system`. A failed audit insert is logged by `AdminAudit`; check those logs if an action succeeded but the history entry is missing. Do not treat the audit list as a substitute for database backups.

The **Bulk jobs → Data retention** panel controls how long uploads, results, and job records remain. The default is 24 hours. Choose 1 hour to 7 days and select **Save retention**; both API replicas and the worker read the new database setting without restarting. Shortening it can remove existing completed jobs at the next minute's cleanup. The operator history records the change. Jobs still actively processing are allowed to finish; old queued or stale running jobs are cleared.
Local bulk files live in the named `azurite-data` Docker volume, so recreating the Azurite container does not erase unexpired results. The worker removes both blobs and job metadata when a job expires. Do not remove this volume separately while its job rows still exist.

`GET /health/live` confirms that the admin process is running; `GET /health/ready` also checks that it can open a database connection. Both are intentionally unauthenticated for local and future orchestrator health checks. `GET /api/system` includes a `checkedAtUtc` timestamp and remains an administrator endpoint outside Development.

The **Automatic maintenance → Storage housekeeping** panel shows the last hourly local storage check, free space on the cache volume, and source archives removed. The first check runs when the admin service starts. A sweep skips archive deletion while a release preparation is queued or running; it also leaves files modified in the last 24 hours alone so a separate loader is not interrupted. The status is available at `GET /api/housekeeping` for administrators. A storage check failure or less than 10% or 5 GiB free is shown as needing attention and logged. This is a local warning, not an external alerting service. PostgreSQL's autovacuum performs routine table maintenance; the importer analyzes new serving data. The bulk worker separately removes expired jobs each minute. The local stack still has no scheduled off-computer backup.

## Update the national data

1. In **Release management**, choose a release from the official current and previous-version catalogues. Use **Check latest** to select the newest official release quickly, or choose an archived national GDA2020 release such as November 2025 from the picker. The picker shows whether each release is already installed. A release older than the live one is a historical replay; selecting it does not change the live API.
2. Select **Prepare selected release**. The portal resolves that exact version from the official catalogue again, downloads the archive, checks its version and PSV headers **before ingestion**, then imports, indexes, and validates the data in the background. The current release continues serving API requests. Leave the local computer and containers running while this completes. If preparation stops, check the message on the page and retry from step 1. A schema-drift error needs an importer compatibility review before retrying.
   For a deliberate historical replay, lower counts than a newer live release are expected. The importer still checks that serving addresses match the archive's supported raw addresses, required national data is present, and geocode coverage meets the threshold. If an already-built historical candidate failed only the old forward count-drop rule, preparing that same release again rechecks its existing tables without a second full import.
3. When the release appears under **Review and activate**, compare its address count and geocode coverage with the live release. Select **Activate** only when the figures look right. The API process stays running during this database switch.
4. If the new data causes a problem, select **Restore** under **Return to the previous release**. This switches the database view back to the retained national release.

After the current release has been accepted, **Storage → Delete previous release data** can remove the retained rollback copy. Type the exact version shown, then select **Delete**. The portal deletes only a retired complete national release, its alias maps, and its serving schema; it does not switch or restart the live API. Preparation must finish first. The action frees roughly the previous release's displayed serving-table size **on each database node** and removes the immediate rollback option. To use that version again, download and import its official archive. The operator history records the deletion. Do not use this control when you still need a fast rollback.

The portal only prepares full national releases. Regional and synthetic data are excluded from its controls. A prepared release is never activated automatically.

## Support and recovery

The portal and API run at `http://127.0.0.1:8081/` and `http://127.0.0.1:8080/`. If the portal does not open, ask the person managing the local Docker stack to check `docker compose ps` and `docker compose logs gnaf-admin`. If the API status is unhealthy, check `docker compose logs api-gateway address-api address-api-b postgres`. Both API containers must be healthy for full API redundancy; one healthy container can still serve requests.

Keep PostgreSQL backups. Release rollback uses retained database schemas and does not replace a backup. Do not manually delete an active or previous national release schema; use the guarded portal control for a retired release.

Run `sh scripts/rehearse-backup-restore.sh` for an isolated recovery check. It creates a disposable HA stack, seeds a small synthetic release, makes a compressed `pg_dump`, restores it into another database, compares the active release and row count, checks a restored ID, forces database B to take over, restarts A as standby, and checks API recovery. A 90-second continuous API read probe records the failure window in `quality/results/recovery_rehearsal.json`. In the 5 October run, 699 of 900 reads succeeded, 201 returned structured `DATASTORE_UNAVAILABLE` HTTP 503, and the longest gap between successes was 20.21 seconds. A sudden primary loss is therefore not seamless; callers should retry 503 with backoff. The script removes only its own disposable containers, volumes, and temporary dump. This tests automatic takeover with a small fixture; off-host backup storage remains to be proven.

For a full data check, run `sh scripts/rehearse-national-restore.sh`. It dumps the installed national database, restores it into a disposable standalone PostgreSQL container, and compares release states, active address count, alias counts, and a sample G-NAF ID. The 5 October run passed with a 1.4 GiB compressed dump and 15,949,543 active addresses. Allow temporary disk space for the dump and an uncompressed database copy. The script removes both after the check. This is a logical restore on the same computer; it does not test off-host backup storage, a measured restore-time objective, or recovery from complete host loss.

The old `addressvalidation_backups` volume was removed during the clean N−3 replay on 6 October 2026. The main local stack currently has no persistent backup volume. The restore rehearsal creates and removes a disposable dump; it is not a standing backup policy. Establish a fresh persistent, preferably off-host backup before relying on this installation for important data.

The database keeps serving tables for the live and up to one previous national release. Activation removes raw import tables from completed national releases, then removes older retired national schemas and completed-release source files from the G-NAF cache. The operator may later delete the previous release as described above. The source ZIP can be downloaded again if a rebuild is needed. The dashboard's database size is **per PostgreSQL node**: streaming replication keeps a second full copy on B. Expect total local storage to exceed the single-node dashboard figure. The history table's "Original ZIP size" describes the downloaded file at import time, even after cleanup.

PostgreSQL automatically promotes the standby after a primary failure. The API reconnects to the new primary; requests during the brief promotion window may fail and can be retried. See [local failover operations](HA-REHEARSAL.md) for role checks and limitations.

The two API containers and gateway run on the same computer. This protects against one API container failing, but a gateway, Docker host, or computer failure still interrupts service. No separate app registration is required for this local routing setup.

The CLI remains available for technical diagnosis: `docker compose run --rm gnaf-loader status` lists releases, and `docker compose run --rm gnaf-loader check` checks the official catalogue.
